# Pixel Cube Lab

**COMP 560 final project implementation design — November 17, 2026**

Status: original implementation plan, retained for context. The implemented solver, application, measurements, and deliverables are documented in [README.md](README.md). Final changes include a monochrome website shell, per-move verification, and a bounded replay of actual search events. The main experiment uses a one-second/100,000-expansion budget; interactive limits are larger.

## 1. Project question and scope

**Research question:** How much do compact admissible heuristics reduce the search effort required to find shortest solutions to a 3×3×3 Rubik’s Cube, under a fixed computational budget?

Build a local-first, browser-based cube solver with pixel-style graphics, a shared command-line experiment runner, and an independently tested cube engine. Implement IDA* and its heuristics ourselves. Use an explicitly credited implementation of Kociemba’s two-phase algorithm as a practical reference solver for harder states.

The core study compares heuristics within the same search implementation. This isolates the effect of heuristic quality. Comparing our solver with the reference solver provides engineering context, but differences also reflect algorithm design, preprocessing, and implementation.

### Required scope

- Standard 3×3 cube, fixed center orientation, all 18 outer-face turns.
- Legal states generated by moves from the solved cube; deterministic seeded scrambles.
- Custom cube state, transitions, notation parser, IDA* search, and pattern databases.
- Four research configurations: zero heuristic, misplaced-cubie lower bound, orientation databases, and orientation plus corner-permutation databases.
- Two-phase reference solver, clearly labeled in the interface and outputs.
- Pixel-style interactive cube; manual turns, scramble input, solver selection, cancel, solution verification, and playback.
- Reproducible experiment corpus, raw results, figures, documented commands, and tests.

### Scope limits

The custom solver targets shallow-to-moderate scrambles. We will measure its practical limit instead of promising fast optimal solutions to arbitrary states. Arbitrary legal states can be submitted to the reference solver, also with explicit resource limits.

Camera recognition, physical robotics, a neural heuristic, accounts, multiplayer, and other cube sizes are deferred. A color-by-color state editor is also deferred: it requires stronger input validation and adds little to the main research question. The application needs no backend or paid API.

### Course connection

Weeks 2–3 supply state-space search, iterative deepening, heuristics, A*, admissibility, and memory tradeoffs. IDA* and pattern databases extend those ideas. The project does not require machine learning to satisfy the AI scope.

## 2. Solver design

### State and move metric

Use a cubie representation, with arrays indexed by location:

```ts
interface CubeState {
  cp: Uint8Array; // 8 corner identities
  co: Uint8Array; // 8 corner orientations, values 0..2
  ep: Uint8Array; // 12 edge identities
  eo: Uint8Array; // 12 edge orientations, values 0..1
}
```

Use the conventional URF, UFL, ULB, UBR, DFR, DLF, DBL, DRB corner ordering; document the edge ordering and orientation convention beside the move tables. Adopt a published convention consistently and credit its source.

Implement the six clockwise face turns as permutation/orientation tables. Derive inverse and half turns by composition. Moves are U, R, F, D, L, B, each with optional prime or 2 suffix. Clockwise means looking directly at the turned face from outside the cube. Whole-cube viewing rotations never change the logical state.

Use the **half-turn metric (HTM)**: a quarter turn, inverse quarter turn, and half turn each cost one move. Every solver, database, plot, and reported solution length must use this metric.

State invariants:

- Every corner and edge identity occurs exactly once.
- Corner orientations sum to 0 modulo 3.
- Edge orientations sum to 0 modulo 2.
- Corner and edge permutation parity agree.
- The goal is identity permutations with all orientations zero.

Provide conversion to and from a documented 54-facelet representation in URFDLB face order. Rendering derives its stickers from the state; it never owns a second independent cube model.

### Baseline heuristic

Let `badCorners` and `badEdges` count cubies that have either an incorrect position or an incorrect orientation, counting each cubie once.

```text
h_simple(s) = max(ceil(badCorners / 4), ceil(badEdges / 4))
```

This is a lower bound because one allowed turn touches only four corners and four edges, so it cannot fix more than four of either kind. Avoid raw misplaced-sticker count as a distance estimate: it does not directly correspond to moves.

### Pattern databases

Generate exact distances from the abstract solved state by breadth-first search over all 18 moves. Each abstraction ignores some aspects of the full state, making its solution distance a lower bound for the original problem.

| Database | Information retained | Entries |
| --- | --- | ---: |
| Corner orientation | Twists of seven corners; eighth determined | 3^7 = 2,187 |
| Edge orientation | Flips of eleven edges; twelfth determined | 2^11 = 2,048 |
| Corner permutation | Positions of all eight corners; orientations ignored | 8! = 40,320 |

Store distances as bytes: 44,555 entries in total, excluding headers, move tables, queues, and build-time memory. Generate rank/unrank functions and coordinate transition tables. Verify complete table coverage and known distances before using a database.

Research variants:

```text
H0:    h(s) = 0                         // IDDFS through the shared IDA* engine
H1:    h(s) = h_simple(s)
H2:    h(s) = max(h_simple, cornerOrientationDB, edgeOrientationDB)
H3:    h(s) = max(H2, cornerPermutationDB)
```

Take the **maximum**, not the sum: one move can improve several abstractions simultaneously. The small tables intentionally omit edge permutation and joint constraints. That is a limitation we can analyze, and a reason not to expect deep arbitrary cubes to be easy.

Version generated files with move convention, HTM metric, table shape, source revision, and checksum. Include a rebuild command. Account for generation and loading time separately from warm search time.

### IDA* implementation

1. Set the first threshold to `h(start)`.
2. Run depth-first search with `f = depth + h(state)`.
3. If `f` exceeds the threshold, return that value as a candidate for the next threshold.
4. If the state is solved within the threshold, return the move sequence.
5. On exhaustion, use the minimum exceeded value for the next iteration.
6. Stop with an explicit status on time, node, cancellation, or depth limits.

Prune consecutive turns of the same face: they reduce to at most one HTM move. Optionally canonicalize adjacent opposite-face turns because they commute; test this separately before enabling it across all methods. Use fixed move ordering in the main heuristic experiment. Do not add a naive global visited set, which can incorrectly discard useful paths across thresholds or search contexts.

Start with preallocated per-depth state buffers to limit allocations. Keep an ancestor-state check if needed for longer cycles. Store search statistics separately from rendering updates. Define `expanded` as a non-goal node admitted by the threshold whose successors are enumerated; define `generated` separately and use these definitions for every custom variant.

With admissible heuristics, complete threshold iterations, and pruning that preserves a shortest solution, a completed custom solve is optimal in HTM. Timed-out or depth-limited runs establish no solution length or impossibility claim.

### Reference solver

Wrap the MIT-licensed `cubejs` implementation of Kociemba’s two-phase algorithm behind a separate adapter. Pin its version and retain its license and attribution. Validate our facelet conversion with known examples before connecting it to the UI.

The reference solver operates on the current state, not the scramble history. Its solutions are valid but not guaranteed shortest. Never use their lengths as ground-truth optimal distances. Never silently substitute a reference result for a custom solver result. Offer an explicit “Try two-phase solver” action after a custom timeout.

Regardless of solver, replay every returned sequence through our cube engine and verify that it solves the exact submitted state before presenting success.

## 3. Application and visual design

### Visual direction

**Pixel Cube Lab** should resemble a focused retro puzzle laboratory: charcoal/navy background, ivory text, sharp panel borders, warm yellow controls, and saturated cube stickers. Use small pixel typography for titles and conventional readable text for descriptions and metrics. Bundle any font with its license; the application should work without external font requests.

Render the cube with an orthographic camera, thick dark cubie gaps, flat materials, and minimal lighting. Use a low internal canvas resolution with nearest-neighbor scaling for the pixel effect. Offer a crisp rendering toggle and respect reduced-motion preferences. Small text and controls remain at normal display resolution.

### Interaction rules

- Initial state is solved, with a suggested six-move seeded scramble.
- Users can generate a scramble or enter standard notation. Invalid tokens are reported without partially applying the sequence.
- Label the number of scramble turns as **scramble length**, never optimal depth.
- Scramble input is applied from solved; manual turns apply to the current state. Make the distinction visible.
- Manual turn buttons and keyboard shortcuts share one move queue. Ignore shortcuts while typing in inputs.
- Solution playback starts from a snapshot of the submitted state. Step backward applies the inverse move; replay resets to the snapshot first.
- Editing or scrambling invalidates the old solution. During active search, editing either requires cancellation or cancels explicitly; late worker replies cannot overwrite newer state.
- Camera movement remains available during search and playback.
- Show initialization, searching, verified solution, timeout, node limit, depth limit, cancelled, and error states distinctly.
- A timeout says “No solution found within this budget,” not “Unsolvable.”
- Progress shows elapsed time, current threshold, and explored nodes. No invented percentage complete.
- Metrics reflect solver work, excluding playback and animation.
- A solved cube returns an empty, valid solution with zero moves.

### Experiments screen

Load checked-in result JSON, plot solved fraction, expanded nodes, and runtime versus scramble length, and provide raw-data downloads. Do not run the full paper benchmark silently in the browser. Include a small optional comparison on the current cube, executing methods sequentially on the same state.

Until experiments have run, display a clear empty state. Demo examples and mock data must never appear as measured findings.

## 4. Technical architecture

### Stack

- TypeScript for the cube engine, custom search, browser app, and benchmark runner.
- Vite for local development and static production builds.
- Three.js for cube geometry, orthographic projection, and face-turn animation.
- Plain HTML/CSS and small UI modules; a UI framework is unnecessary for this scope.
- Web Workers for browser solving and initialization.
- Node.js for headless benchmarks using the same solver code.
- Vitest for meaningful engine/search tests; browser interaction checks for the demo.
- A script-generated SVG figure pipeline for deterministic, portable paper figures.

Pin dependencies and commit a lockfile. Test the chosen runtime versions on the team’s machines before documenting support. No hosting service or backend is needed; a static build can later be served locally or on GitHub Pages.

### Worker contract

```ts
type SolveRequest = {
  type: 'solve';
  requestId: string;
  state: SerializedCubeState;
  algorithm: 'ida-zero' | 'ida-simple' | 'ida-orientation' |
             'ida-combined' | 'two-phase';
  limits: { timeMs: number; nodeLimit: number; maxDepth: number };
};

type SolveResult = {
  type: 'result';
  requestId: string;
  status: 'solved' | 'timeout' | 'node-limit' | 'depth-limit' | 'error';
  moves: string[] | null;
  verified: boolean;
  optimality: 'proven' | 'not-proven' | 'not-applicable';
  stats: {
    initializationMs: number;
    searchMs: number;
    expanded: number | null;
    generated: number | null;
    iterations: number | null;
    lastThreshold: number | null;
  };
};
```

Use null for statistics unavailable from the reference library. Add progress and error messages with the same request ID. Never transfer a typed array in a way that detaches the main thread’s live cube state; serialize a snapshot.

A synchronous search running inside a worker cannot process a cancellation message until it yields. For the first implementation, cancel by terminating that worker and recreating it. Enforce custom limits inside the search and add a parent-side watchdog for the reference solver. Cache immutable database assets so reinitialization is predictable. Record cancellation in UI/run metadata; discard any result with an obsolete request ID.

## 5. Experimental protocol

### Hypotheses

1. Pattern database heuristics reduce node expansions relative to the simple lower bound.
2. Adding corner permutation helps on some states where orientation alone gives a weak bound.
3. Stronger heuristics extend the solvable range within the budget, but their evaluation overhead may dominate on trivial states.
4. The two-phase reference solver reaches deeper states efficiently, with solution quality that must be measured rather than presumed optimal.

These are hypotheses, not results to build the paper around in advance.

### Corpus

- **Correctness set:** exhaustively enumerate distinct states to depth 3 with BFS. This gives known optimal distances for shallow tests. Include fixed identities and a solved-state case.
- **Pilot:** five seeded instances each at scramble lengths 2, 4, 6, 8, 10, and 12. Use this only to select feasible final budgets and scope.
- **Main study:** target twenty unique states per chosen length, initially the same six lengths. Generate and freeze a new seeded corpus after the pilot.
- **Reference demonstration:** a separately labeled set of longer random-walk scrambles, such as length 25, for practical solving. Do not mix it into shallow exact-depth claims.

Generate scrambles without consecutive turns of the same face, deduplicate by canonical state, and record the exact sequence and state. This is a random-walk corpus, not uniform sampling from all cube states. A 12-turn scramble can have a much shorter solution. Use the true optimum as an axis only where it is independently established by completed optimal search or BFS.

### Fair comparisons

- Run H0–H3 on identical states with fixed move ordering and identical pruning.
- Initial proposed per-instance limits: 10 seconds, 2 million expanded nodes, and maximum HTM solution depth 20. Freeze final limits after the pilot and publish them.
- The reference solver uses the same wall-clock limit; its unavailable node count is recorded as null. Document its internal depth limit separately.
- Build/load tables before warm runs; publish cold initialization and database sizes separately.
- Run one solver at a time; do not benchmark simultaneous workers against one another.
- Warm up the runtime, then repeat measured runs three times with a seeded shuffled method order. Use one machine and record CPU, OS, Node version, commit, dependency lock hash, and database/corpus hashes.
- Record failed and timed-out instances. Do not average only easy successes and imply those numbers characterize the full corpus.

### Raw record

One JSONL row per run: run ID, instance ID, exact state/scramble, seed, scramble length, solver/configuration, budgets, preprocessing time, elapsed search time, expanded/generated counts, threshold iterations, status, returned sequence, HTM length, independent verification result, optimality status, and environment metadata.

### Main figures and table

1. Solved fraction within budget versus scramble length.
2. Expanded nodes versus scramble length for custom methods, with log scale where useful and failures marked separately.
3. Paired runtime comparison on common solved instances, alongside coverage so selection effects are visible.
4. A compact table of preprocessing cost, database size, and verified solution length. Compare reference length to optimum only on instances whose optimum is known.

Use medians and spread across instances, with per-instance repetition medians for timing. Treat timeouts as censored failures; do not report the timeout cutoff as a completed solve time. Store exact plot inputs with the figures.

## 6. Correctness and acceptance criteria

### Cube and notation tests

- Each face turn repeated four times returns the original state.
- A move followed by its inverse is identity; two half turns are identity.
- A sequence followed by its reversed inverse is identity.
- Known turns match trusted facelet fixtures, not only our own inverse implementation.
- Random legal sequences preserve all orientation and permutation invariants.
- Serialization and facelet conversion round-trip.
- Cross-check random sequences with the independently maintained reference cube model.
- Parse whitespace and supported suffixes; reject unsupported tokens atomically.

### Search and database tests

- Rank/unrank round-trip every coordinate value in each small database.
- Abstract transitions agree with projection of full-state transitions.
- BFS reaches every expected abstract state and assigns zero to the goal.
- Check database consistency across all abstract transitions: `h(s) <= 1 + h(next)`.
- On the shallow exact corpus, all heuristic values are at most the known optimal distance.
- Custom methods return verified shortest sequences on the exact corpus when allowed to complete.
- Pruning preserves shortest lengths on the shallow exact corpus.
- Every reported solved result replays to the goal, including the reference adapter.
- Limits produce explicit failure statuses without false solutions.

### UI checks

- Manual, scramble, solve, and playback paths keep logical state and stickers synchronized.
- Play/pause, next, previous, and replay work at both ends of the move list.
- Reset or a new scramble invalidates stale solutions and progress.
- Cancellation remains responsive while a worker is busy.
- Resizing and camera motion do not alter the cube state.
- Keyboard navigation, focus indicators, readable contrast, reduced motion, and labeled face controls work.
- Production build loads worker and database assets under a repository subpath.

The main acceptance gate is a verified end-to-end solve from the current state, a passing correctness suite, and a clean-checkout experiment command that regenerates the paper’s figures. A successful animation alone is insufficient evidence of solver correctness.
